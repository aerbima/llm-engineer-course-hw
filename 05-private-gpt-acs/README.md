# Enterprise Private GPT для проектировщика СКУД

Локальный RAG-чат-бот: отвечает на вопросы по внутренним стандартам и регламентам
только на основе загруженных документов. LLM, эмбеддинги, векторная база и интерфейс
работают на одном компьютере, без внешних платных API.

> Шаблон отчёта. Места с пометкой **ЗАПОЛНИТЬ** заполняются по результатам ваших запусков.

## Архитектура

```
data/docs/*.md, data/raw/*.pdf
   │  ingest.py: MarkdownHeaderTextSplitter → RecursiveCharacterTextSplitter (800 / 120)
   ▼
ChromaDB (chroma_db/, косинусная метрика) ◄── эмбеддинги bge-m3 (Ollama)
   │  retriever.py: Top-K по близости
   ▼
rag.py: переписывание вопроса по истории → поиск → порог → промпт с контекстом → LLM (Ollama)
   │  memory.py: память диалога (none / window / summary_buffer)
   │  sessions.py: журнал диалога в JSONL
   ▼
app.py: интерфейс Gradio на http://127.0.0.1:7860
```

## Запуск

Нужно: Windows 10/11, [Ollama](https://ollama.com), [uv](https://docs.astral.sh/uv/), Git.

```powershell
ollama pull qwen3.5:9b
ollama pull bge-m3
uv sync                     # или: uv add -r requirements.txt
copy .env.example .env
uv run check_llm.py         # 1. модель отвечает локально
uv run ingest.py            # 2. документы → ChromaDB
uv run calibrate.py         # 3. подобрать SCORE_THRESHOLD и записать его в .env
uv run app.py               # 4. интерфейс: http://127.0.0.1:7860
uv run experiments.py       # 5. тесты трёх типов и Top-K → results/
uv run pytest -q            # проверка логики без Ollama
```

## Структура

| Файл | Назначение |
|---|---|
| `config.py` | настройки из `.env` |
| `llm.py` | создание LLM и эмбеддингов (Ollama или OpenAI-совместимый сервер) |
| `check_llm.py` | проверка, что модель отвечает локально |
| `ingest.py` | загрузка документов, чанкинг, запись в ChromaDB |
| `retriever.py` | семантический поиск Top-K |
| `prompts.py` | системный промпт, промпт переписывания вопроса, промпт сводки |
| `memory.py` | память диалога: окно и сводка + буфер |
| `sessions.py` | журнал диалога в JSONL и восстановление |
| `rag.py` | RAG-цепочка |
| `app.py` | интерфейс Gradio |
| `calibrate.py` | подбор порога близости |
| `experiments.py` | тесты и замер Top-K |
| `tests/test_offline.py` | тесты логики без модели |

## Данные

`data/docs/` — учебные документы (вымышленные стандарт СТП-СКУД-01, регламент РЕГ-ПД-02 и FAQ).
`data/raw/` — PDF производителей и нормативы: в репозиторий не попадают.

### Влияние Top-K

В ходе экспериментов влияние параметра Top-K на качество оказалось незначительным. Для всех значений Top-K (1, 2, 4 и 8) система корректно выполнила 7 из 8 тестовых сценариев. Единственный сбой наблюдался для вопроса о длительности нормоконтроля и, вероятно, связан с особенностями автоматической проверки ответа, а не с качеством поиска документов.

Рост Top-K не привёл к повышению точности, однако увеличил объём контекста, передаваемого в модель. Среднее число входных токенов выросло с 437 при Top-K=1 до 2344 при Top-K=8. Это сопровождалось увеличением времени генерации ответа.

Эксперимент с памятью показал, что режимы window и summary_buffer успешно восстанавливают контекст уточняющего вопроса. Запрос "А что делать, если считыватель дальше?" был преобразован в более полный вариант с указанием ограничения по длине линии Wiegand. Несмотря на это, автоматическая проверка диалога не была пройдена, поскольку ответ модели не содержал ожидаемой подстроки "RS-485".


## Вывод

В рамках проекта для локальной RAG-системы были выбраны модели **qwen3.5:9b** и **bge-m3**. Модель qwen3.5:9b обеспечивает хорошее соотношение качества ответов и требований к ресурсам, позволяя запускать систему на пользовательском оборудовании без необходимости использования облачных сервисов. Для построения векторного поиска выбрана модель bge-m3, которая показывает высокое качество создания эмбеддингов для документов на разных языках и хорошо подходит для поиска релевантных фрагментов в базе знаний.

По сравнению с облачными API локальное развёртывание имеет ряд особенностей. Основными ограничениями являются вычислительные ресурсы устройства: система работает на процессоре Intel Core i7-13700F, 16 ГБ оперативной памяти и видеокарте NVIDIA GeForce RTX 3050 с 4 ГБ видеопамяти. При таких характеристиках скорость генерации ниже, чем у крупных облачных моделей, а размер доступной локальной модели ограничен объёмом памяти. Кроме того, локальная модель может чаще допускать неточные ответы и галлюцинации, особенно при недостатке контекста или отсутствии релевантных данных в базе знаний.

Главным преимуществом локального решения является защита корпоративных данных. Все документы, эмбеддинги и пользовательские запросы обрабатываются на локальном компьютере и не передаются сторонним облачным провайдерам, что снижает риск утечки конфиденциальной информации. Однако полностью риски не устраняются: они остаются связанными с безопасностью самого рабочего места, возможным несанкционированным доступом к файлам базы знаний, ошибками настройки системы и сохранением данных на локальных носителях. Таким образом, локальное развёртывание обеспечивает более высокий уровень контроля над корпоративными данными по сравнению с использованием внешних облачных сервисов.
