## 1. Что настроено

| Параметр | Значение | Зачем |
|---|---|---|
| Модель | `yandexgpt-lite/latest` | REST API Yandex Cloud, метод `foundationModels/v1/completion` |
| `temperature` | `0.1` | минимум «креативности» — нужны факты, а не варианты |
| `maxTokens` | `1500` | предел длины ответа; JSON по одному документу укладывается с запасом |
| `MAX_CHARS` | `12 000` символов | предел длины одного куска документа |
| `CHUNK_OVERLAP` | `500` символов | перекрытие кусков, чтобы ИНН или сумма не разрезались пополам |
| Повторы запроса | до 3 раз при 429 / 500 / 503, пауза 2 → 4 c | устойчивость к лимитам и сбоям API |

**Схема пайплайна**

```
data/docs/*.txt
  → clean_text          очистка пробелов и пустых строк          (data_prep.py)
  → split_into_chunks   нарезка длинных документов с перекрытием (data_prep.py)
  → build_messages      system + user (правила, few-shot, текст) (prompts.py)
  → ask_yandexgpt       запрос к API, повторы                    (llm_client.py)
  → parse_response      вырезать JSON → json.loads → pydantic    (llm_parser.py)
  → merge_results       склейка кусков без дублей                (pipeline.py)
  → check_grounding     есть ли ИНН/КПП/суммы в исходном тексте  (llm_parser.py)
  → results/<имя>.json
```

**Три слоя проверки ответа модели**

1. **Формат** — `clean_json_response` убирает Markdown-обёртку ```` ``` ```` и текст вокруг `{…}`, затем `json.loads`.
2. **Схема** — pydantic-модель `Extraction`: типы полей, списки; ИНН — 10 или 12 цифр, КПП — 9 цифр.
3. **Опора на текст** — `check_grounding`: цифры каждого ИНН, КПП и суммы должны встречаться в исходном документе, иначе предупреждение «возможна галлюцинация».

## 2. Итоговые промпты

Модель получает два сообщения: `system` (роль и правила) и `user` (что извлекать + один пример + сам документ). Код — [`prompts.py`](prompts.py).

### Системный промпт

````text
Ты — строгий и точный AI-помощник опытного юриста.
Твоя задача — извлекать факты из текста юридического документа без искажений и выдумываний.
Строгие правила:
1. Бери данные ТОЛЬКО из текста. Ничего не додумывай и не вычисляй.
2. Если сведений нет в тексте — ставь null (для списка — пустой список []).
3. ИНН, КПП, суммы и даты переписывай символ в символ так, как они записаны в тексте.
4. Отвечай ТОЛЬКО валидным JSON-объектом. Без пояснений, без Markdown, без ```.
````

### Пользовательский промпт (шаблон)

Вместо `{few_shot_text}`, `{few_shot_json}` и `{text}` функция `build_messages` подставляет пример и очередной кусок документа.

```text
Извлеки из текста документа именованные сущности:
- document_type: вид документа (договор поставки, договор на выполнения проектных работ, NDA, доверенность, решение суда и т.п.)
- contract_number: номер договора/документа или null
- parties: стороны — role (роль в документе), name (название или ФИО), inn (ИНН), kpp (КПП); нет значения поля — null; если ничего нет — пустой список [], не null
- dates: signing_date (дата подписания), valid_from (начало действия), valid_until (окончание действия); нет значения — null
- amounts: суммы — value (число без пробелов), currency (код: RUB, USD, EUR, KZT, BYN), source_text (как в тексте), purpose (за что); нет значения поля — null; если ничего нет — пустой список [], не null
- obligation_terms: сроки обязательств — obligation (что сделать), term (срок как в тексте), deadline_date (конкретная дата или null); если ничего нет — пустой список [], не null

Пример.
Текст:
{few_shot_text}
Ответ:
{few_shot_json}

Теперь обработай настоящий документ. Верни только JSON той же структуры.
Текст:
{text}
```

### 4.2. OCR-шум (06_ocr_noisy) — модель «чинит» текст непоследовательно

Фрагмент исходного текста (целиком; `0`/`О`, `1`/`l`, `3`/`З` перепутаны, как после плохого распознавания):

Полученный JSON (фрагмент):

Ошибки и предупреждения пайплайна:

- ошибка схемы: `Схема: parties.0.inn: Value error, ИНН должен состоять из 10 или 12 цифр, получено: '6165 2233 44'`
- предупреждение: `INN 6165 2233 44 (ООО «ЮгРемонт») нет в тексте — возможна галлюцинация`
- предупреждение: `KPP 616501001 (ООО «ЮгРемонт») нет в тексте — возможна галлюцинация`
- предупреждение: `KPP 616401001 (ООО «Дон Офис») нет в тексте — возможна галлюцинация`
- предупреждение: `Сумма «1 200 000 (один миллион двести тысяч) руб.» не найдена в тексте`

Что не так:

- КПП `61650l001` → `616501001` и сумма `1 2О0 000` → `1 200 000` — модель исправила OCR. По смыслу это верно, но нарушает правило 3 промпта («символ в символ»), поэтому `check_grounding` не нашёл эти цифры и выдал предупреждения.
- В то же время дата `О2 июля 2О26 г.` и номер `3З/26` оставлены с буквами вместо цифр — одно и то же правило применено к разным полям по-разному.
- ИНН `6165 2233 44` переписан с пробелами и не прошёл валидацию схемы (10 цифр). Поскольку при ошибке схемы `parse_response` возвращает непроверенный словарь, этот ИНН попал в итоговый результат.
- Предупреждение по ИНН — ложное срабатывание моего кода: `check_grounding` ищет значение с пробелами в строке из одних цифр; нужно сравнивать `only_digits(v)`.

Как исправить: добавить шаг нормализации OCR **до** LLM (в числовом контексте `О→0`, `l→1`, `З→3`); после LLM нормализовать ИНН/КПП до цифр кодом; в `check_grounding` сравнивать только цифры; при ошибке схемы — повторный запрос к модели с текстом ошибки валидации.

### 4.4. Плейсхолдеры анонимизации (court_1)

Фрагмент исходного текста:

Полученный JSON (фрагмент): `"signing_date": "г. Биробиджан <ДАТА1>"`

Что не так: в датасете даты заменены на `<ДАТА1>`, и модель записала в дату город вместе с плейсхолдером. Как исправить: в промпте — «значения вида `<ДАТА…>`, `<АДРЕС>`, `<НОМЕР>` считай отсутствующими (null)», плюс постобработка кодом.

### 4.5. Нормализация дат вместо копирования

| Документ | В тексте | В JSON |
|---|---|---|
| 07 | «с 1 февраля 2026 г. по 31 января 2027 г.» | `valid_from: "01.02.2026"`, `valid_until: "31.01.2027"` |
| 01 | «14» марта 2026 г. | `"14 марта 2026 г."` (кавычки «» убраны) |
| 04 | «вступает в силу с даты подписания» | `valid_from: "5 октября 2026 г."` — дата выведена, а не взята из текста |

Ошибки не критичные (даты верные по смыслу), но это нарушение правил 1 и 3 промпта, и формат дат в результатах получается разный. Как исправить: хранить два поля — дату как в тексте и нормализованную ISO-дату (`2026-02-01`), которую считает код, а не модель.

### 4.6. Модель игнорирует запрет на Markdown

Все 11 ответов пришли в обёртке ```` ``` … ``` ````, хотя системный промпт прямо запрещает Markdown. JSON всё равно разобран, потому что `clean_json_response` вырезает содержимое между фигурными скобками. Вывод: на текстовые инструкции о формате полагаться нельзя. Надёжнее режим структурированного ответа API: у метода `completion` в `completionOptions` есть поля `jsonObject` и `jsonSchema` (JSON Schema, которой должен соответствовать ответ) — схему можно сгенерировать из pydantic-модели (`Extraction.model_json_schema()`).

### 4.7. Сломанная структура: `null` вместо списка (найдено и исправлено)

В первом прогоне пустой документ `05_doverennost.txt` (0 символов) ушёл в API, и модель ответила `"parties": null, "amounts": null, "obligation_terms": null`. Pydantic отклонил такой ответ, непроверенный словарь дошёл до `merge_results`, и пайплайн упал с `TypeError: 'NoneType' object is not iterable`. Причина — противоречие в промпте: правило 2 требует `[]` для списков, а описание полей говорило «нет значения — null». Исправлено тремя изменениями: однозначная формулировка в промпте («если ничего нет — пустой список [], не null»), защита `part.get(key) or []` в склейке и пропуск пустых документов без запроса к API.

### 4.8. Чего не проверял

Стабильность ответов (несколько прогонов одного документа) в этом прогоне не измерялась. При `temperature = 0.1` ответы должны быть почти одинаковыми, но это нужно подтвердить отдельным экспериментом.

## 5. Вывод: YandexGPT против Natasha / spaCy

| Критерий | LLM через API (YandexGPT) | Natasha / spaCy |
|---|---|---|
| Набор сущностей | любой, задаётся текстом промпта: роль стороны, ИНН, КПП, срок обязательства | готовые модели размечают в основном PER, LOC, ORG; у Natasha есть отдельные экстракторы дат, денег и адресов; юридические сущности требуют разметки и дообучения |
| Связи между сущностями | из коробки: «этот ИНН принадлежит Поставщику», «этот срок относится к оплате» | нужны отдельные правила или модели |
| Нормализация | сумма прописью → число и код валюты (01, 03, 07) | отдельный код |
| Подготовка | без обучающих данных: промпт + один пример | для юридического домена — разметка корпуса |
| Галлюцинации | есть: сумма из цитаты закона (court_2), «исправленный» OCR (06), выведенная дата (04) | модель размечает только то, что есть в тексте |
| Формат ответа | инструкции о формате нарушаются (11 из 11 ответов в Markdown); нужен парсер и валидация | структура гарантирована библиотекой |
| Воспроизводимость | `latest` — версия модели меняется на стороне Яндекса | фиксированная версия модели — одинаковый результат |
| Скорость и стоимость | секунды на документ, оплата за токены: 1 266–4 526 токенов на документ; на коротких документах бо́льшая часть — постоянный промпт с примером | быстро на CPU, бесплатно |
| Конфиденциальность | документ уходит в облако | всё локально |

**Вывод.** Для извлечения реквизитов из договоров LLM-подход заметно удобнее: структуру со связями «сторона — ИНН — роль», нормализованные суммы и сроки он дал без обучения, на 9 из 10 документов — без формальных замечаний. Но «как есть» в production его использовать нельзя: прогон показал смысловые ошибки, которые проходят формальную валидацию (court_2), непоследовательную работу с зашумлённым текстом (06) и игнорирование инструкций о формате.

Чтобы довести пайплайн до production, нужно:

1. структурированный ответ через `jsonSchema` вместо просьбы в промпте;
2. детерминированная обработка кодом: нормализация OCR до LLM, ИНН/КПП/даты — после LLM;
3. повторный запрос при ошибке схемы с текстом ошибки;
4. более строгая проверка опоры на текст (в том числе для сумм прописью);
5. фиксированная версия модели вместо `latest` и регрессионный набор документов с эталонными ответами;
6. выборочная проверка человеком.

Разумная архитектура — гибрид: регулярные выражения и классический NER (Natasha, spaCy) для того, что хорошо формализуется (ИНН, КПП, даты, суммы), а LLM — для смысла и связей (кто есть кто, к чему относится срок), с перекрёстной сверкой результатов. Если документы конфиденциальны, нужно отдельно решить, допустима ли их передача в облако.
